01

The idea, explained simply

Explain it like I'm five

Imagine a school exam. Real engineers already sat it: they wrote code, then wrote tests — little programs that check the code behaves properly.

We took 104 of those finished exams, hid the answer sheets, and asked a robot to sit the same exam. Then we marked both papers.

The robot scored the same as the humans.

That's the whole project. The complicated parts are only there to make the exam fair: finding real projects, hiding the answers properly, and marking without cheating.

Getting this wrong is easy. In 15% of our first attempt the tests weren't properly hidden, because the code only looked for a folder literally named Tests/. Those runs were thrown away.
02

Building the dataset

To mark the exam you need answer sheets. Swift had none, so we made them.

Explain it like I'm five

Somewhere on the internet there are millions of Swift files. Some are recipes (the code). Some are taste-tests (the tests that check the recipe).

They're all jumbled in one giant pile, and nobody had ever matched them up. We did: 20,801 matched pairs.

Java has had this since 2022. Swift didn't have it at all.

What actually gets published

Not the code. The dataset ships pointers: which repository, which file paths, a fingerprint of each file, and everything we measured. Anyone can rebuild the real files from the two public sources using the included script.

That's why it's 3.2 MB instead of 95 MB — and why there's no licensing problem. We're publishing the matching, not somebody else's work.

03

How the whole thing runs

Three phases, each a gate. If a gate fails you stop there, having spent hours instead of weeks.

04

What TestForge actually does

Explain it like I'm five

An AI can write a test, but it never checks whether the test works. It hands you something that looks right and walks away.

TestForge doesn't. It writes the test, then tries to build it. If it breaks, it reads the error and tries again. If it still can't fix it, it puts the file aside so your project keeps working.

That's the difference: the AI writes; TestForge checks.

What this proves

Coverage parity with the engineers who wrote the code. Unattended, at roughly ₹45 per project.

And 5,263 test cases against the humans' 4,073 across 90 repositories — 29% more, because it works through the whole project rather than whatever file you happen to paste in.

What it doesn't

The scaffolding doesn't make the model write better Swift. A plain prompt's output survives at 93.2%; TestForge's at 91.1%. That gap is noise.

What the loop buys is scale and safety — more tests, and a build that can't break. Not better prose from the model.

And the honest counterweight: in 24 of 88 repositories — 27% — TestForge produced nothing usable at all.
06

Does it work without the cloud?

The same tool, the same 19 repositories, driven by a 30-billion-parameter model running entirely on a laptop.

Explain it like I'm five

The robot needs a brain. You can rent a very fast one over the internet, or use a slower one that lives on your own computer.

The one on your computer is free and never sends your code anywhere — which matters enormously if you work somewhere that code isn't allowed to leave.

We tried both on the same work. The local brain is slower, and gives up more often. But when it does the job, it does it just as well.

The number that decides it

Gemini produced usable tests on every single repository. The local model produced nothing on 58% of them — and typically spent 20 to 60 minutes discovering that. One repo ran for 127 minutes and kept nothing.

But it isn't simply worse

On four repositories the local model beat the cloud one — 35 files against 32 on one, 31 against 25 on another. When it engages properly it writes more, not less.

The behaviour is bimodal: excellent or empty, rarely in between.

The honest summary for a workplace that can't send code out: on-device is viable, not equivalent. Roughly two-thirds the keep rate, half the hit rate, and ten times the wall clock. For code that isn't allowed to leave the building, that trade is usually still worth making — but say the numbers rather than just "it runs locally".
07

The finding we didn't go looking for

Public Swift code is far more out of date than anyone assumes — and that has consequences for every model trained on it.

2.7%
still compile

Of 20,801 real test pairs, only 569 build on Swift 6.4.

0.6%
use Swift Testing

Apple's current framework, shipped 2024. 126 of 20,801 pairs.

0.4%
use async/await

5 of 1,287 source files. Swift concurrency shipped in 2021.

7.2%
are Swift 2 or 3

Syntax no current compiler will accept at all.

Each of those was confirmed across two independently collected corpora — one scraped via Google BigQuery, one via Software Heritage — so it isn't an artefact of how one dataset was built.

The consequence is uncomfortable. Models learn Swift from this material. They will confidently write the dialect it contains: XCTest rather than Swift Testing, synchronous code rather than async, and occasionally syntax that stopped compiling in 2016.

This is why the benchmark targets XCTest rather than Swift Testing — comparing against a human baseline means speaking the human baseline's language.
08

Eleven bugs that produced plausible wrong answers

Not one of them crashed. Every single one returned a number that looked like a finding.

  1. swift build writes errors to stdout; we read stderr and saw 375 blank failures.
  2. DuckDB applies USING SAMPLE before WHERE — every sample was the wrong size.
  3. DuckDB connections aren't thread-safe. Concurrent use returned empty results: 82 phantom missing files.
  4. A database view over 4 GB re-scanned it on every query. Minutes became hours.
  5. A join missed one equality check and produced 1,070 pairs spliced from two different corpora.
  6. A build rate measured per-repository was applied to per-file counts. The estimate was double the truth.
  7. An interrupted run left half-written files that broke every later run — at zero cost, so it looked like a clean failure.
  8. Coverage counted the test runner itself, so a project with no tests read as 99.73% covered.
  9. Totals were read from the wrong part of a report; a blanket except hid the error and silently disabled the budget cap.
  10. HTTP 429 means rate-limited or out of credit. We retried the second for twenty minutes.
  11. Two runs wrote to one filename. The second silently overwrote the first, and the comparison table showed one arm twice.
The pattern

The tell was almost always a suspiciously round number — $0.0000, zero rows, exactly 100%.

A tool that genuinely tried and failed still costs money, still returns rows, still lands somewhere untidy. Perfectly clean output usually means nothing ran.

SwiftTestPairs — 20,801 Swift source-to-test pairs, applying the methods2test (MSR 2022) methodology to a language that had no equivalent. Built with DuckDB, SwiftSyntax and TestForge. Benchmarked on gemini-3.8-flash and, on-device, on qwen3-coder:30b — four arms in all, marked identically.

Figures on this page are measured, not estimated. Where an arm could not be measured it says so.
