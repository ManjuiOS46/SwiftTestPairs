Where the data came from

Every filter, every number, and exactly what ends up on Hugging Face — so you can answer any question about it.

01

Why this had to exist

The short version

You cannot mark an exam without an answer sheet.

To prove a machine writes good tests, you need real tests, written by real engineers, for real code — thousands of them, matched up so you know which test belongs to which file.

Java has had exactly this since 2022 (Microsoft's methods2test, 780,000 pairs). Swift had nothing. So the benchmark couldn't be run until the answer sheet was built.

That is the whole reason this dataset exists. It isn't a scrape for its own sake — it's the measuring instrument, and it had to be built before anything could be measured.

It turns out to be useful on its own too: anyone studying Swift testing, training a model, or benchmarking a different tool can use the same pairs. That's why it's worth publishing rather than keeping local.

Using two mattered more than expected. They were collected by different routes, so anything true in both is unlikely to be an artefact of how one was built — which is what makes the findings about Swift's staleness defensible rather than anecdotal.

Both are Swift source only. No Xcode project files, no assets, no Info.plist. That single fact shaped everything downstream — it's why only SwiftPM packages could ever be verified.
03

The seven steps, and why each one

  1. Load everything

    Both corpora into one database. 3,208,002 files

    DuckDB, because it reads compressed files directly without unpacking 4 GB first.

  2. Keep only permissively licensed code

    MIT, Apache-2.0, BSD, ISC and similar. Everything else dropped. − 2.7M files

    Why: GPL code carries obligations that would follow anyone who used the dataset. Unlicensed code is "all rights reserved" by default — not free to use, whatever people assume.

  3. Remove vendored third-party trees

    Anything under Pods/, Carthage/, vendor/, ThirdParty/.

    Why: An MIT-licensed repository routinely contains other people's libraries. Those aren't the project's own code, and pairing against them would be meaningless.

  4. Sort every file into three buckets

    TEST (imports XCTest and has test methods), TEST_SUPPORT (mocks and fixtures), SOURCE (everything else).

    Why the middle bucket: mocks live in test folders but aren't tests. Counting them as tests would inflate every number.

  5. Match each test to the code it tests

    By naming convention — FooTests.swift → Foo.swift — plus an index of which file declares which type, for the cases where they don't line up. 23,957 pairs

    The declaration index only added 4.4%. Swift projects follow one-type-per-file more strictly than expected.

  6. Remove duplicates — twice

    Exact duplicates first, then near-duplicates by similarity. − 3,156 pairs

    Why this is not optional: the two corpora overlap 62.6% at pair level. Left in, the same test would land on both sides of a train/test split and any model trained on it would be scored on work it had already seen.

  7. Split by repository, never by file

    80/10/10 into train / validation / test. 20,801 pairs

    Why: files from one project share conventions and helpers. Splitting by file would leak a project's style across the boundary. Split by repo, and a project is wholly on one side. Verified: zero pairs straddle.

Then one extra pass: every pair whose repository has its own Package.swift was actually built with swift build --build-tests. 569 passed. Those are marked tier 2 — the only ones anyone should benchmark on.

Notice what is missing

There is no code in the row. Only where to find it, a fingerprint to check it's the right file, and what we measured.

That is deliberate. The Swift code belongs to the people who wrote it and is already published by others. What didn't exist — and what you built — is the matching.

It's also why the whole dataset is 3.2 MB instead of 95 MB, and why there's no licensing problem with publishing it.

The included resolve.py rebuilds the real files from the two public corpora and checks each one against its fingerprint. It was tested on all 569 verified pairs: every one resolved, every fingerprint matched.

06

What you can and can't say about it

✓

"The first public Swift source-to-test pair dataset."

Checked. Java, Python and Julia have equivalents; Swift had none.

✓

"Applies the methods2test (MSR 2022) methodology to Swift."

Accurate, and stronger than claiming novelty — it shows you know the field.

✓

"20,801 pairs from 3.2M files; 569 verified to compile on Swift 6.4."

All measured, all reproducible from the published pipeline.

✓

"Only 2.7% of real-world Swift test pairs still compile."

The most interesting thing here. Confirmed across two independent corpora.

✕

Don't say it's training data.

0.6% use Swift Testing, 7.2% contain Swift 2/3 syntax. Train on it and you teach a model the dialect Apple is retiring. It is a benchmark.

✕

Don't quote costs.

The tool under-reports spend roughly 4× — reasoning tokens are billed but never appear in its usage figures. The other numbers are safe; this one isn't.

✕

Don't call the licence labels a guarantee.

They're repository-level. An MIT repo can still contain third-party code under other terms. The card says so; say the same.

One thing to settle first: publishing is public and effectively permanent. You were going to check your employment agreement before pressing the button — that's still the right order.
